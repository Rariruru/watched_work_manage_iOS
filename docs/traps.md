# 実行環境の罠とコード規約

前作 Collecie iOS の振り返り（上田のローカルにある非公開の文書 `next-project-CLAUDE.md`。リポジトリには無いので探さなくてよい。必要な内容はこのファイルに要約してある）から、**このプロジェクトに当てはまるものだけ**を要約した。
このプロジェクトで新しく踏んだものは、ここに追記する（出典は「本プロジェクト YYYY-MM-DD」）。
コメントには「知らないと踏む罠」だけを書き、`⚠️` を付けて grep できるようにする。

## ⚠️ Expo Go では Apple でサインインが使えない（出典: 本プロジェクト 2026-09-26）
- 公式の文書（SDK 57）は「Included in Expo Go」と書いているが、App Store の Expo Go（`executionEnvironment: storeClient`）には `ExpoAppleAuthentication` のネイティブモジュールが入っていなかった
- `isAvailableAsync()` はモジュールが無いとき**エラーを出さずに false を返す**。「OS が使えないと言った」と見分けが付かない
- 対策: `src/app/sign-in.tsx` で `requireOptionalNativeModule("ExpoAppleAuthentication")` を見て、「機能が入っていない」を別に出す。Apple でのサインインを試すのは EAS の開発用ビルドから
- 文書に書いてあっても、実機で見るまでは「使える」と書かない

## ⚠️ react-query は失敗を黙って「一時停止」にする（出典: 本プロジェクト 2026-09-26）
- 既定の `networkMode: "online"` では、react-query がオフライン・画面が前面にないと判断すると、再試行を `paused` にして止める。**エラーにも成功にもならず、読み込み中の表示のまま止まる**
- Web のプレビューで、接続先が無いのに40秒以上読み込み中のままになって見つけた。`fetchStatus` を出して `paused` と分かった
- 対策: `src/api/queries.ts` で `networkMode: "always"`。オフラインの扱いはアプリ側（`src/api/useSave.ts`・`src/api/errors.ts`）で「接続できません」を出す

## ⚠️ supabase-js は GET を自動で再試行する（出典: 本プロジェクト 2026-09-26）
- postgrest-js 2.117 は、GET の通信失敗と 503 / 520 のときに、1秒・2秒・4秒の間隔で最大3回再試行する。**失敗が画面に出るまで約7秒かかる**。POST・RPC は再試行しない
- react-query 側でも再試行すると待ち時間が倍になるので、`retry: false` にしてある。止めたい読み込みは `.retry(false)`

## ⚠️ TypeScript 6 は `@types/*` を自動で読まない（出典: 本プロジェクト 2026-09-26）
- `node:test` などの型が見つからないエラーになる。`@types/node` を入れても直らない
- アプリ全体に Node の型を混ぜないよう、テストファイルの先頭に `/// <reference types="node" />` を書く

## ⚠️ Expo の API は記憶で書かない（出典: 本プロジェクト 2026-09-26）
- SDK ごとに名前や置き場所が変わる。SDK 57 は画面を `src/app/` に置き、未ログインの出し分けは `Stack.Protected`。書く前に `node_modules` の型定義か、`https://docs.expo.dev/versions/v57.0.0/` を見る
- パッケージは `npx expo install <name>` で入れる（SDK に合う版が選ばれる）

## ⚠️ エラーを握り潰さない（出典: next-project §1）
- `if (data)` だけで分岐しない。エラーのときに「0件」と見分けが付かなくなる
- **「取得できなかった」と「0件だった」を必ず区別する**（受け入れ基準 13）
- 既定値（`?? []` 等）で続けるときも、同時に警告ログは出す
- 握り潰してよいのは「失敗しても本体を続けるべきもの」だけ。そのときは理由をコメントに書く

## ⚠️ 同じものを2か所に置かない（出典: next-project §2）
- 判定の正はサーバ（Supabase の行レベルセキュリティ・制約）の1か所。アプリ側の判定は表示の出し分けだけに使う
- 「本人しか読めない」をアプリ側の絞り込みだけで実現しない（受け入れ基準 14）
- どうしても複製するなら、両方のファイル冒頭に「複製である・相手のパス・片方だけ直すな」を書く

## ⚠️ 順序を守る：DB → サーバ → アプリ（出典: next-project §3）
- 本プロジェクト 2026-09-26: 一覧の取得（`src/api/works.ts` の `WORK_SELECT`）に新しい列・表を足すと、SQL の適用前は一覧ごと失敗する。取得を分ける代わりに、`src/api/errors.ts` がエラーコード（42703・42P01・42883・PGRST200・PGRST202）を見て「データベースの更新が適用されていません」と出すようにした。**新しい列を足したら、アプリより先に SQL を適用する**
- まだ存在しない列を既存のクエリに混ぜると、クエリごと失敗して別の症状（全部0件・未ログイン扱い）に化ける
- 新しい列は既存のクエリに混ぜず別に取り、失敗しても既定値で続けられる形にする

## ⚠️ ローカルに持った古いデータ（出典: next-project §4）
- 応答や記録を端末に保存（キャッシュ）する場合、前のバージョンの形のデータが起動直後に返る
- 項目を足したら、その項目は「無いことがある」と永久に考える。無いときにどちらへ倒すかを毎回決める
- 入れ直すと消えるので開発機では踏みにくい。前のバージョンを一度起動した端末で確認する

## ⚠️ サーバ側の処理を足したときの応答（出典: next-project §5）
- Supabase の Edge Functions など自前の処理を足す場合、未デプロイのときの応答は 404 とは限らない
- 成功ステータスだけで判定せず「期待する形の応答か」を見る。失敗時はステータス・Content-Type・本文の先頭を警告ログに残す
- 新しい処理はアプリから叩く前に本番へ出す。迷ったら `curl` で直接叩いて切り分ける

## ⚠️ 環境変数・秘密の値は手で貼らない（出典: next-project §6）
- ビルドサービスの対話プロンプトに貼ると先頭の1文字が飲まれることがある。本番ビルドだけが起動直後に落ちる
- ファイルから読ませて非対話で設定し、設定後にローカルの値と機械で突き合わせる（長さ・完全一致）
- 環境ごと（本番 / プレビュー / 開発）に独立しているので全部確認する
- Supabase の service_role key はアプリに入れない。リポジトリにもコミットしない

## ⚠️ 起動直後に落ちるとき（出典: next-project §7）
- グローバルなエラーハンドラで捕まえようとしない。モジュールを1つずつ読み込んで OK / NG を画面に並べると1回のビルドで分かる
- クラッシュログは「落ちた」と記録されたスレッドだけを見る

## ⚠️ 速く確認できる環境は本番と別物（出典: next-project §8）
- シミュレーター・プレビューで動いても実機で動くとは限らない（逆もある）。位置情報・写真の許可・カメラは特に差が出る
- 日付・数値を環境をまたいで文字列経由で変換しない。前作は日付の文字列パースが実機だけ失敗し、日付を扱う7画面が一斉に壊れた（訪問日・視聴日が該当）
- 「プレビューで確認した」を「確認した」と書かない。実機で見るまでは未確認

## ⚠️ 写真のDB行を消してもStorage実体は消えない（出典: 本プロジェクト 2026-09-27）
- PostgreSQLの外部キー連鎖は `record_photos` の行には効くが、Storageオブジェクトには効かない
- 記録・作品削除ではアプリが対応するオブジェクトを削除し、アカウント削除ではservice roleを持つ `delete-account` Edge Functionが `record-photos` と `work-covers` の本人フォルダを削除してからAuthユーザーを削除する
- Edge Functionをデプロイせずにアプリだけ更新すると、アカウント削除に失敗する。DBマイグレーションと関数を先に反映する

## ⚠️ 審査は「辿り着けるか」で落ちる（出典: next-project §10）
- アカウント削除・利用規約・プライバシーポリシーは、すべての状態から辿り着けることを確認する
- 到達性の表: `docs/design/wireframe-v3.html` の「到達性チェック」

## ⚠️ 検証の作法（出典: next-project §13）
- ビルドの出力をパイプで切らない（`| head` はビルドを途中で殺す）。ファイルに落としてから検索する
- 成果物を grep して文字列の反映を確かめない（エスケープされて見つからないことがある）。ソース側で確認する
- バックグラウンドで上げたプロセスは必ず落とす。**自分が上げたものだけ**

## コード規約（出典: next-project §11）
- コンポーネントは画面ごとのディレクトリに入れる。直下にファイルを置かない
- 「組み立て（純関数）」と「見た目」を分ける。条件分岐を追うときに前者だけ読めば足りるようにする
- ⚠️ 大文字小文字だけで名前を分けない（Windows が同一視して落ちる）
- 1ファイル 300 行を超えたら分割する。機能を足すときも巨大ファイルに積まない
- 同じ見た目が2か所に出たらコピーせず共通化する（シート・カード・フィルタが特に重複する）
- ⚠️ 新規に作る前に既存を探す
- 色・余白は必ずトークン経由。生の色コードを直接書かない
- ミューテーション（保存・削除）には成功・失敗どちらの通知も必ず付ける（受け入れ基準 15）
