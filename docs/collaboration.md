# Codex 単独開発ルール

> 適用開始: 2026-09-27
> この文書は、本リポジトリの開発体制と作業手順の正とする。

## 1. 体制

本リポジトリは、2026-09-27 以降、Codex が単独の開発エージェントとして担当する。

Codex の担当範囲:

- 要件整理と受け入れ基準
- データ契約、ドメイン用語、集計定義
- UI／画面設計と実装計画
- アプリ、API、SQL、マイグレーションの実装
- テスト、静的検査、動作確認
- README、運用文書、既知の罠の更新
- Git の差分確認、コミット、ユーザー指示時の push

人間の担当範囲:

- プロダクト判断が必要な未決事項の決定
- 本番への SQL 適用
- App Store Connect、本番ビルド、提出
- 本番シークレットや外部サービスの重要操作
- push の指示

## 2. 文書と実装の正

優先順位は次のとおり。

1. `docs/contracts.md`
2. `docs/requirements.md`
3. `docs/plans/*.md`
4. 実装コード、SQL、テスト

矛盾がある場合は、上位の文書を確認・更新してから、下位を一致させる。実装だけを先に正として文書を追認しない。ただし、既存実装から判明した事実は調査材料として使い、意図を確認したうえで正へ反映する。

担当ファイルは分割しない。Codex はリポジトリ全体を編集できるが、ユーザーの未コミット変更や無関係な差分を保持する。

## 3. 標準ワークフロー

### 3.1 着手

1. `git pull --rebase` で最新化する
2. `git status` と直近の履歴を確認する
3. `AGENTS.md`、`requirements.md`、`contracts.md`、`traps.md` を読む
4. `docs/handoff/` に残る `status: open` を確認する

### 3.2 要件と計画

- 振る舞いが変わる場合は `requirements.md` を先に更新する
- データ、列挙値、単位、必須条件、集計、削除連鎖が変わる場合は `contracts.md` を先に更新する
- 要件の変更理由と日付を変更履歴へ残す
- 未決事項は推測せず「未定」とする。実装結果が大きく変わる場合はユーザーへ確認する
- 複数層にまたがる機能、危険な変更、ロールバックを考える必要がある変更は `docs/plans/<機能名>.md` を作る
- 計画には目的、前提、非スコープ、変更対象、作業順序、検証、移行／ロールバック、未決事項を書く
- 計画の状態は `draft`、`ready`、`done` を使う

### 3.3 実装

原則として、次の依存順で進める。

1. データ契約、DB、マイグレーション
2. サーバー処理、API、型
3. アプリの状態管理と画面
4. テスト
5. README、`traps.md`、関連文書

小さく独立した修正は計画書を省略してよい。ただし、要件や契約が変わる場合の文書更新は省略しない。

### 3.4 検証

変更範囲に応じて以下を実行する。

```powershell
npm run lint
npm run typecheck
npm test
npm run export:web
```

DB 変更では、マイグレーションの順序、既存データ、RLS、型、削除連鎖を確認する。UI 変更では、対象画面だけでなく主要導線と空・読込・失敗状態も確認する。

### 3.5 完了

1. 差分と `git status` を確認する
2. 要件、契約、実装、テストの整合を確認する
3. 1つの論理変更としてコミットする
4. コミット本文の最後に `AI: codex` を付ける
5. push 指示がある場合のみ、直前に `git pull --rebase` してから push する

## 4. 旧引き継ぎファイル

`docs/handoff/` は、2026-09-26 までの Codex／Claude Code 共同開発の履歴兼バックログとして保持する。

- 新しい引き継ぎファイルは原則作らない
- `status: open` は未反映事項として扱い、関連作業時に正の文書と実装へ直接取り込む
- 内容を反映した後は、元ファイルへ反映先と完了日を追記して閉じる
- 過去の経緯を失わないため、既存ファイルを一括削除・書き換えしない

## 5. Git 運用

- `main` へ直接コミットする。ブランチと PR は原則使わない
- 作業開始前と push 前に `git pull --rebase` する
- force push はしない
- コンフリクト時は、内容と所有者を確認して解消する。判断できない変更を破棄しない
- 無関係な差分、生成キャッシュ、秘密情報をコミットしない
- push はユーザーの明示指示がある場合だけ行う

## 6. 安全境界

Codex は次を実行せず、必要な手順と検証結果を人間へ渡す。

- 本番 DB への SQL 適用
- App Store Connect の操作
- 本番ビルドと提出
- 本番シークレットの作成・変更
- 取り消しにくい外部サービス操作
