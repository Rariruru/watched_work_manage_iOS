# AI 同士の共同開発ルール

このリポジトリは、2人の開発者がそれぞれ別の AI を使って進める。
**このファイルが両者の共通ルールの正。** `CLAUDE.md`（Claude Code 用）と `AGENTS.md`（Codex 用）はここへの索引だけを持ち、中身を書き写さない。

作成: 2026-09-26（Claude 側が初版を作成。変更は下の「このファイルの変え方」に従う）

---

## 1. 登場人物と担当

| | 人間 | AI | 担当する工程 |
|---|---|---|---|
| 上流 | 共同開発者 | **Codex** | 要件・データ契約・画面設計・実装計画（WHAT / WHY と、どう分けて作るか） |
| 下流 | 上田 | **Claude Code** | 実装・SQL（マイグレーション）・テスト・実機で踏んだ罠の記録 |

- **AI は相手の AI と直接やり取りしない。** やり取りはすべてリポジトリ内のファイル（§4）と PR を通す
- **判断が割れたら、決めるのは人間。** AI 同士で決着させない

## 2. ファイルの持ち主

持ち主だけがそのファイルを書き換える。持ち主でない側が直したいときは、直接編集せず §4 の連絡ファイルを書く。

| ファイル | 持ち主 | 中身 |
|---|---|---|
| `docs/requirements.md` | Codex | 何を作るか（WHAT / WHY）・受け入れ基準 |
| `docs/contracts.md` | Codex | データ契約・ドメイン用語。**単位・綴り・必須項目・集計の定義はここが正** |
| `docs/design/` | Codex | 画面設計・ワイヤーフレーム（「実装の正ではない」と日付を書く） |
| `docs/plans/<機能名>.md` | Codex | 実装計画（§3 の形式） |
| アプリのコード・テスト | Claude | |
| `supabase/`（マイグレーション SQL） | Claude | `contracts.md` をスキーマに落としたもの |
| `docs/traps.md` | Claude | 実行環境の罠とコード規約 |
| `README.md` のセットアップ手順 | Claude | |
| `docs/handoff/` | 両者 | 連絡ファイル（§4） |
| `docs/collaboration.md`・`CLAUDE.md`・`AGENTS.md` | 両者 | 変えるときは §7 |

- ⚠️ **食い違ったときの優先順位: `contracts.md` ＞ `requirements.md` ＞ `plans/` ＞ コード。** コードが文書と違うなら、コードの誤りとして扱う。文書の側が誤りだと思うなら §4 で持ち主に伝える
- `docs/requirements.md`・`docs/contracts.md` の初版は、2026-09-26 に Claude 側の `/spec` で作った。以後の持ち主は Codex

## 3. 1つの機能の流れ

1. **Codex** が `requirements.md`・`contracts.md` を更新し、`docs/plans/<機能名>.md` を書く → `spec/<機能名>` ブランチで PR → 上田が確認してマージ
2. **Claude** がマージ済みの計画を読んで実装する → `feat/<機能名>` ブランチで PR → 共同開発者が確認してマージ
3. 途中で要件の穴に気づいたら、どちらの側も §4 の連絡ファイルを書く

`docs/plans/<機能名>.md` に必ず書くこと（下流が推測で埋めずに済むように）:

- 対象の受け入れ基準の番号（`requirements.md` の §5）
- 触る `contracts.md` の節と、新しく足す列挙値・必須項目
- 画面の一覧と、各画面の空状態・エラー状態
- 分割の順序（DB → サーバ → アプリ。`traps.md` の「順序を守る」）
- この計画で**やらないこと**

⚠️ **計画が無い機能は実装しない。** Claude は計画を自分で書かず、連絡ファイルで Codex に依頼する。ただし上田が「計画なしで進めてよい」と明示したときは、その旨を PR に書いて進める。

## 4. 連絡ファイル（`docs/handoff/`）

相手の持ち物を直したいとき・質問したいときは、ここに1件1ファイルで書く。

- ファイル名: `YYYY-MM-DD-<差出人>-<短い英語名>.md`（例: `2026-10-03-claude-episode-zero.md`）。差出人は `codex` / `claude`
- 形式:

```markdown
---
from: claude            # codex / claude
to: codex
status: open            # open → answered → closed
blocking: yes           # yes = 回答が来るまでその部分の実装・設計を止める
refs: requirements.md 基準34, contracts.md「シーズン」
---

## 何が起きたか
<見つけた事実。推測と事実を分けて書く>

## 提案
<こうすればよい、という案。複数あれば並べる>

## 回答
<受け取った側がここに書く。書いたら status を answered にする>
```

- 回答するのは `to` の側。回答したら `status: answered`
- **`closed` にしてよいのは、持ち主が自分のファイルに反映し終えたとき。** 反映したら、そのファイルの変更履歴にこの連絡ファイルの名前を書く
- ⚠️ **連絡ファイルを消さない。** `closed` のまま残す。なぜそう決めたかの記録になる
- ⚠️ **`blocking: yes` の部分を推測で埋めて進めない。** 特に `contracts.md` に関わるもの（列挙値・必須項目・単位・削除の連鎖）は、推測で作るとデータを作り直すことになる。関係しない部分は進めてよい
- 急ぐ連絡ファイルは、それだけの小さな PR（`handoff/<短い英語名>` ブランチ）で出す。作業中の PR に混ぜてもよいが、そのときは PR の説明に書く
- 作業を始めるときは、まず `docs/handoff/` の中から、自分宛て（`to`）で `open` のものを探して確認する

## 5. Git

- `main` に直接コミットしない。すべてブランチから PR を出し、**相手側の人間**が見てからマージする
- ブランチ名: `spec/…`（Codex）・`feat/…` と `fix/…`（Claude）・`handoff/…`（両者）
- 1つの PR には、持ち主が同じファイルだけを入れる（`docs/handoff/` は例外）。上流の文書とコードを同じ PR に混ぜない
- PR の説明に書くこと: どの AI が作ったか・関係する受け入れ基準の番号と連絡ファイル・確認したことと確認していないこと
- ⚠️ コミットする前に `git diff --cached` で、中身が自分の変更だけになっているかを見る
- push とマージは人間がやる
- **マージボタンを押すのは、PR を作っていない側の人間。** 「両方の人間が OK」が要る PR（§7）でも同じ。作った側は GitHub で Approve できないので、PR にコメントで「OK」と書く
- 2人とも、このリポジトリの collaborator（push 権限）であること。権限が無いとブランチの push・Approve・マージができない

## 6. 両者が守ること

- 文書は UTF-8（BOM なし）・改行 LF で書く
- 進捗の一覧表を書かない（実装が進むほど古くなり、事実と逆のことを書く表になる）
- 決定を変えたら、変えた事実と理由を残す（古い記述を消すだけにしない）。`requirements.md` は末尾の「変更履歴」、`contracts.md` は該当の項目に「変更: YYYY-MM-DD 理由」
- 決まっていないことは、推測で断定して書かない。`requirements.md` の「未決事項」に書くか、§4 で聞く
- 「ブラウザで確認した」「シミュレーターで確認した」を「確認した」と書かない。実機で見るまでは未確認
- **人間しかやらないこと:** 本番の Supabase への SQL の適用・App Store Connect の操作・本番ビルドと提出・秘密の値（service_role key 等）の扱い。AI はコマンドと手順を用意するところまで

## 7. このファイルの変え方

- どちらの側も変更を提案できる。変更は `docs/collaboration.md` だけを含む PR にし、**両方の人間が OK してから**マージする
- 変えたら下の「変更履歴」に日付と理由を書く
