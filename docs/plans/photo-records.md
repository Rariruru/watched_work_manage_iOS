# 写真付き記録（聖地巡礼・グッズ・イベント）実装計画

## 目的

作品に紐づく聖地巡礼・グッズ・イベントを、名前・日付・写真・メモ・任意の位置とともに作成、閲覧、編集、削除できるようにする。対象は `requirements.md` の受け入れ基準 3・8・9・11・14・15・19〜22・29・30。

## 現在地

- アカウント、作品、シーズン、各話、感想・評価は実装済み
- 写真付き記録のDB、API、画面、ストレージ処理は未実装
- Supabaseの既存マイグレーション3件は、リポジトリにはあるが本番適用は未確認

## スコープ

- 作品に紐づく3種類の記録の作成・一覧・詳細・編集・削除
- 必須の名前、任意の日付・メモ・写真
- 聖地巡礼とイベントだけが持てる任意の緯度・経度
- 作品詳細と作品一覧の「＋」からの作成導線
- 作成途中で既存作品を選ぶ導線と、新しい作品を作って戻る導線
- 写真／位置情報の権限を拒否した場合の継続と設定案内
- 写真の個別再試行・取り外し
- 本人だけが読み書きできるRLSと、作品／アカウント削除時の連鎖

## 非スコープ

- 記録の公開、共有、通報、フォロー
- 聖地マップ、現在地による初期位置、経路案内
- 写真からの日付・位置の自動入力
- 記録をシーズンや各話へ紐づけること
- 1つの記録を複数作品へ紐づけること
- オフライン保存と下書き同期
- Android、Web向けの製品提供

## 確定した契約

1. 記録種類のDB値は `pilgrimage` / `goods` / `event`
2. 写真は1記録4枚まで。アップロード前に長辺2048pxへ縮小し、1枚10MBを入力上限とする
3. アップロード前に位置情報を含むEXIFを除去する
4. 一部アップロード失敗中は記録を保存済みにせず、入力を画面内に保持する。閉じるときは破棄確認を出し、サーバー側の下書きは作らない
5. 作成後の種類と紐づく作品は初版では変更不可

2026-09-27、本人が推奨案を承認。`contracts.md` と `requirements.md` へ反映済み。

## データ契約案

### `records`

- `id`: UUID、主キー
- `user_id`: UUID、必須、本人の識別
- `work_id`: UUID、必須、`works` 削除時に連鎖削除
- `kind`: 記録種類の列挙値、必須
- `name`: 前後の空白を除いて1文字以上、必須
- `occurred_on`: `date`、任意。入力欄の初期値は今日
- `memo`: `text`、任意。空文字は値なしへ正規化
- `latitude` / `longitude`: 任意。片方だけは不可。グッズでは両方とも値なし
- `created_at` / `updated_at`: 必須

### `record_photos`

- `id`: UUID、主キー
- `record_id`: UUID、必須、記録削除時に連鎖削除
- `storage_path`: 必須、一意
- `position`: 1以上の整数。記録内で一意
- `created_at`: 必須

写真は非公開バケット `record-photos` に置き、パスを `{user_id}/{record_id}/{photo_id}.jpg` とする案。メタデータ行とStorageオブジェクトの双方に本人限定ポリシーを設定する。

## 実装順序

### 1. DBとストレージ

- `records`、`record_photos`、制約、インデックス、更新日時、RLSを追加
- 親作品と同じ本人にだけ記録を追加できる制約をRPCまたはトリガーで保証
- 種類と位置の整合、緯度経度の範囲、写真上限をDBでも保証
- 作品削除、記録削除、アカウント削除時のメタデータとStorage実体の削除手順を用意
- 別利用者からの読み書き拒否と削除連鎖を確認するSQLを追加

### 2. ドメインとAPI

- `src/domain/types.ts` に記録と写真の型を追加
- 名前、日付、位置、写真枚数、種類別条件を純関数で検証
- 一覧取得とCRUDを `src/api/` に追加し、取得失敗と0件を区別
- 写真は選択、加工、アップロード、メタデータ保存の状態を個別管理
- 途中失敗時に成功済みファイルを再利用し、重複アップロードを防ぐ

### 3. 画面

- 作品詳細に種類別の記録一覧と追加導線を追加
- 作品一覧の「＋」に、作品追加と3種類の記録追加を並べる
- 記録フォームで作品選択、新規作品作成、名前、日付、写真、メモ、位置を扱う
- グッズでは地図を表示しない
- 権限拒否時も写真なし／手動位置で保存可能にし、設定アプリへの案内を出す
- 保存・削除の成功／失敗通知、読み込み失敗の再試行、空状態を実装

### 4. 検証

- 純関数テスト: 必須名、日付、位置、種類、写真上限
- SQL確認: RLS、親子の所有者一致、削除連鎖、写真上限
- 画面確認: 受け入れ基準 8・19〜22・29・30
- 回帰確認: 作品削除、アカウント削除、通信失敗、既存の作品・評価画面
- `npm run lint`
- `npm run typecheck`
- `npm test`
- `npm run export:web`
- 写真選択、カメラ、位置情報、設定アプリ遷移はiPhone開発ビルドで確認する。Web確認を実機確認の代わりにしない

## 移行とロールバック

- 追加テーブル中心の変更とし、既存データの書き換えは行わない
- マイグレーションは既存3件の後へ追加する
- 本番適用前に既存3件の適用状況を確認する
- ロールバックではアプリの導線を先に無効化し、保存済み写真を退避してからテーブル／バケットを削除する。利用者データを確認なく破棄しない
